# ch11 困难评估集设计

日期：2026-10-10
分支：`ch11`

## 1. 目标

现有评估集（`evals/rag_eval.jsonl`，240 道可答题 + 60 道不可答题）上，四种检索策略差距很小。本章新增一套 240 题的困难评估集，与原题集并列报告。困难题集针对单路检索的已知弱点设计，用来展示 hybrid + rerank 方案在难题上的表现。

### 1.1 用户的决定

- 新题集与原题集并列报告，不替换原题集（用户选 A）。
- 只用现有生产知识库，不加干扰文档（用户选 A）。
- 主指标：MRR、R@1、R@5（用户把 R@3 换成 R@5）。Faithfulness 作次要指标。
- 题量固定 240 题。
- 合成模型：DeepSeek（`.env` 中没有 Anthropic 密钥）。

### 1.2 现有题集差距小的原因

数据来自 `evals/reports/rag_eval_20261009-193611.md`：

1. 天花板效应：知识库约 190 段，四种策略 R@5 在 0.962–0.992 之间，MRR 在 0.909–0.987 之间。
2. 标注太宽：例如 A01 有 26 个来源键，命中任意一个都算对，排序好坏测不出来。
3. E_multi 每题至少 2 组事实，按组计算时 R@1 最多 0.5，四种策略都在 0.45 左右。
4. 题目很少针对单路检索的弱点。

## 2. 公正性约束

本节的规则优先于其他各节。目的：保证新题集上的数字经得起追问。

1. 合成代码（`evals/hard_set/`、`scripts/synth_hard_set.py`）不导入 `app.knowledge.retrieval`、`app.knowledge.milvus`、`app.knowledge.rerank`、`app.knowledge.embeddings`。测试检查这一点。
2. 种子选择、过滤和标注都不看任何检索结果。
3. 题集通过人工抽查后冻结：提交 `evals/rag_eval_hard.jsonl` 和 manifest（含 SHA-256），然后才跑第一次检索。冻结后不改题、不删题、不改标注。
4. 如果人工抽查发现问题，修改 Prompt 或过滤规则后整批重新合成，不手改单题。
5. 第 7 节的预期结果在冻结前写定。跑完后逐条对照，结果不符也如实报告。
6. README 写明困难题集的构造方式，并保留原题集的表。

## 3. 题集结构

4 个桶，每桶 60 题，每题只有 1 组来源键（单事实题）。不设多事实题，原因见 1.2 第 3 条。

| 桶 | 题号 | 设计 | 针对的弱点 |
|---|---|---|---|
| `H1_sibling` | `H1_01`–`H1_60` | 问某型号的某项属性；同品类其他型号有同名段落 | dense：同名段落向量几乎相同。BM25：「X3」同时出现在 X3 和 X3 Pro 段落中 |
| `H2_colloquial` | `H2_01`–`H2_60` | 只描述现象或场景，不用目标段落的标题和关键词 | BM25：没有字面重合 |
| `H3_buried` | `H3_01`–`H3_60` | 长段闲聊中只有 1 个稀有术语决定答案 | dense：句向量被闲聊稀释 |
| `H4_specific` | `H4_01`–`H4_60` | 通用文档看起来相关，但只有型号段落给出正确答案 | 不能精排的策略：通用段落容易排第 1 |

所有题的 `difficulty` 字段写 `hard`。报告中困难题集不输出「策略 × 难度」表。

## 4. 种子池

种子 = 目标段落 + 干扰段落 + 考点。代码按固定随机种子（`SEED = 20261010`）从 MySQL `knowledge_chunks` 中确定性地选出，只取文档来源（不含 `mined`、`flywheel`）。来源键用 `app.knowledge.retrieval.source_key` 的同一规则；合成代码不能导入该模块，所以 `evals/hard_set/` 中复制这条规则，并用测试比对两者输出一致。

| 桶 | 目标段落 | 干扰段落（代码指定） |
|---|---|---|
| H1 | 商品手册 24 个型号 × 5 个方面（120 段） | 同品类其他型号的同名方面段落 |
| H2 | 型号「常见故障」段落、商品 FAQ、退货政策、售后手册的场景类段落 | 无固定干扰段落 |
| H3 | 退货政策、售后手册、FAQ 中含稀有术语的段落（例如价格保护、以旧换新、套装退货、发票换开、上门取件） | 无固定干扰段落 |
| H4 | 型号「保修」「退换规则」段落；非默认型号（不是 X3、T3、L1、C5）的「参数」「续航」段落 | 对应的通用段落：售后手册「保修期」、退货政策「品类退换货规则」「质量问题退货」「七天无理由退货」、对应品类的商品 FAQ |

选种规则：

- 每桶按品类分层抽样，8 个品类尽量平均。
- 同一桶内，一个目标段落最多出 2 题，2 题的考点必须不同。
- 不同桶可以共用目标段落。
- 每桶种子池按确定顺序排列。前 60 个种子先用，淘汰后按顺序补位。

## 5. 合成流水线

```
seeds.py   → 种子池（确定性）
prompts.py → DeepSeek 出题（关闭思考，json_mode，{"query": "..."}）
filters.py → 机械过滤（纯函数）
labels.py  → 标注补全（LLM）+ 桶约束检查
           → 不通过：同一种子最多重试 3 次，再失败按顺序换下一个种子
           → evals/rag_eval_hard.jsonl + evals/rag_eval_hard.manifest.json
```

### 5.1 出题 Prompt

每桶一个 Prompt，每个 Prompt 带 2 个手写示例。Prompt 的输入：目标段落全文、考点、干扰段落标题（H1、H4）。约束：

- H1：问题必须写出目标型号，问的事实在干扰段落中有不同的值。
- H2：用顾客口吻描述现象或场景，不用目标段落标题和关键词。
- H3：60–150 字的闲聊，稀有术语只出现 1 次，其余内容不涉及目标段落的事实。
- H4：问题必须写出目标型号，用通用说法提问（例如「保修多久」），不点明章节名。

### 5.2 机械过滤

| 桶 | 规则 |
|---|---|
| 全部 | 问题非空，长度 ≤ 200 字（H3 ≤ 150 字）；与本桶已有问题不重复 |
| H1、H4 | 含目标型号的规范写法或词表别名；不含同品类其他型号 |
| H2 | 问题与目标段落标题的字符二元组重合率为 0；与目标段落正文的字符二元组重合率 ≤ 0.15（阈值写在 `filters.py` 常量中）。计算前从两边去掉型号名，问题可以写型号 |
| H3 | 长度 60–150 字；LLM 从目标段落中选 1 个术语（2–8 字）并返回；术语必须出现在目标段落中，在问题中恰好出现 1 次，并且在全部文档中最多出现在 3 个来源键里（稀有度检查） |

字符二元组重合率 = 问题二元组中出现在目标文本二元组集合中的比例。计算前去掉标点和空白。

### 5.3 标注补全

由代码列出候选段落。候选范围等于生产检索的过滤范围，只依赖知识库结构，不依赖检索：

- 问题含型号时：该型号所属品类的全部段落 + 通用段落（约 60 段）。生产检索在这种情况下只搜这两部分。
- 问题不含型号时：全部文档段落（约 185 段）。

同一来源键的多个分块合并为 1 个候选。

LLM 收到问题和候选段落（编号、标题、正文），返回 `{"answers": [编号, ...]}`：能完整回答问题的段落。之后代码检查：

1. 目标段落必须在 `answers` 中，否则淘汰。
2. H1：同品类其他型号的段落不能在 `answers` 中，否则淘汰。
3. H4：通用段落不能在 `answers` 中，否则淘汰。
4. `answers` 超过 3 个来源键时淘汰。原因：题目必须指向具体事实，避免 A01 那种宽标注。
5. 通过后，来源键组 = `answers` 中全部段落的来源键。

### 5.4 输出

`evals/rag_eval_hard.jsonl` 每行：

```json
{"id": "H1_01", "bucket": "H1_sibling", "difficulty": "hard", "query": "...", "relevant": [["商品手册 > 蓝牙耳机 > X3 Pro 续航"]]}
```

`evals/rag_eval_hard.manifest.json`：生成日期、模型名、git commit、`SEED`、Prompt 文本的 SHA-256、各桶各步淘汰数、被换掉的种子列表、jsonl 的 SHA-256。

### 5.5 错误处理

- 上游调用用 `ChatOpenAI` 的 `max_retries`（SDK 指数回退）。
- 单个种子失败只记入 manifest，不中断整批。
- 某桶种子用完仍不足 60 题时，脚本不写 jsonl，退出码 1。不放宽过滤规则。
- `--check` 只校验已冻结文件：格式、题数、桶分布、来源键存在于 MySQL、SHA-256 与 manifest 一致。

## 6. 评估改动

- `evals/rag_eval_set.py`：按题集选择校验规则。困难题集题号格式 `H[1-4]_\d{2}`，桶 H1–H4 各 60 题，每题恰好 1 组来源键，无不可答题。
- `evals/rag_metrics.py`：增加 4 个困难桶名，归入可答题。
- `evals/run_rag_eval.py`：
  - `--set {base,hard}`，默认 `base`，原有行为不变。
  - `--gen-repeat N`，默认 1。Faithfulness 按 N 次生成取平均，报告列出每次的值。只有第 1 次写 `faith_cases`。
  - 困难题集没有不可答题，跳过门槛扫描。报告标题写明题集名称。
- 检索策略、Query 理解、`exclude_mined=True` 与原题集完全相同。

## 7. 冻结前写定的预期

方向性预期，不预测具体数值：

1. 全部 240 题：hybrid_rerank 的 MRR 和 R@1 在四种策略中最高。
2. H1：hybrid_rerank 的 R@1 高于 dense 和 BM25。
3. H2：BM25 的 R@1 和 MRR 在四种策略中最低。
4. H3：dense 的 R@1 和 MRR 低于 BM25。
5. H4：hybrid_rerank 的 R@1 在四种策略中最高。
6. 至少 1 个桶中，四种策略的 R@5 都 ≥ 0.95（R@5 接近天花板，差距主要在 R@1 和 MRR）。

评估脚本在报告末尾自动逐条写「符合 / 不符合」和对应数值（`evals/hard_set/expectations.py`）。

## 8. 人工抽查

冻结前，用户抽查 20 题：每桶按题号取第 5、20、35、50 题，再从全部 240 题中按 `SEED` 随机取 4 题。用户检查三点：问题像真实顾客说的话；标注正确；题目属于本桶的设计。

如果有题不合格，按第 2 节第 4 条处理。

## 11. 测试

- `filters.py`：每条规则的通过与淘汰用例。
- `seeds.py`：同一 `SEED` 两次输出相同；分层抽样；同一目标段落每桶最多 2 题。
- 来源键规则与 `app.knowledge.retrieval.source_key` 输出一致。
- 标注补全的桶约束检查（用 `RunnableLambda` 替代 LLM）。
- 合成代码不导入第 2 节第 1 条列出的模块（静态检查 import）。
- `rag_eval_set.py` 困难题集校验；`--set hard` 和 `--gen-repeat` 的参数与报告输出。
- Prompt 本身不写单测，用第 8 节的人工抽查验证（CLAUDE.md 非可单测代码的例外）。

## 12. 交付与验收

1. `uv run python scripts/synth_hard_set.py` 生成题集，退出码 0。
2. 用户完成人工抽查，提交冻结文件。
3. `uv run python scripts/synth_hard_set.py --check` 退出码 0。
4. `uv run python evals/run_rag_eval.py --set hard --stage all --gen-strategies all --gen-repeat 2 --concurrency 3` 写入报告。
5. 报告含第 7 节逐条对照。
6. README 两份和 `facts.ts` 更新，`uv run pytest -q` 与前端测试通过。
